## 0. 面试主线：是什么、为什么、怎么做

面试介绍这个项目时，建议始终围绕下面三句话展开：

### 是什么（What）

这是一个面向运营、电商和普通创作者的在线低代码设计平台。用户可以搜索模板、选择设计场景、进入在线编辑器修改文字和图片，保存为自己的设计并导出；平台还提供 AI 图片/视频生成、图片抠图、团队协作、分享和会员额度等能力。

从系统角度看，它是一个**前后端分离、真实数据驱动、带复杂编辑状态的 SaaS Web 应用**：前端负责页面和编辑器交互，后端负责认证、业务规则、并发一致性、AI 任务和持久化。

### 为什么做（Why）

业务上，很多运营和电商用户需要高频制作海报、商品图和活动素材，但不会使用专业设计软件。平台通过模板和场景降低创作门槛，通过 AI 缩短从需求到素材的时间，通过团队协作减少反复沟通。

工程上，做成真实全栈系统是因为静态页面解决不了以下问题：

- 用户登录、作品和会员权益需要持久化；
- 模板搜索、收藏、最近使用和首页推荐需要服务端数据；
- 编辑器必须保存可恢复的画布内容，刷新或换设备不能丢失；
- AI 生成需要保护密钥、记录任务状态并处理失败；
- 多人同时编辑需要权限、版本控制和冲突提示。

### 怎么做（How）

采用 React 19 + TypeScript + Vite 的前端和 Spring Boot 3 + Java 21 的后端，使用 Axios/TanStack Query 完成数据请求，使用 Spring Security + JWT 做认证，MyBatis-Plus 访问 H2/MySQL。

核心做法可以概括为四点：

1. **用 Canvas JSON 表示作品**：模板和用户作品共用 `version/width/height/layers` 协议，保存到 `user_design.canvas_json`。
2. **用 revision 乐观锁保证保存不互相覆盖**：保存请求带当前版本号，后端通过条件更新判断是否冲突，冲突返回 409，前端保留本地草稿。
3. **用异步任务承载 AI**：先写入 `ai_task` 返回 `taskId`，后台调用 Provider，前端轮询并展示成功或失败原因。
4. **用分层和多重权限保护业务**：Controller 接口校验参数，Service 校验用户、团队和额度，Security 负责 JWT/角色拦截，数据库查询再校验资源归属。

### 30 秒三问回答

> 是什么：一个在线低代码设计平台，用户可以基于模板或场景创建设计，在线编辑、保存和导出，并使用 AI 和团队协作能力。
>
> 为什么：目标是降低非专业用户的设计门槛；工程上必须解决作品持久化、权限、AI 异步和多人并发，而不是只做一个静态页面。
>
> 怎么做：前端用 React 管理编辑器状态，后端用 Spring Boot 提供 `/admin` API，画布用 JSON 持久化，保存用 revision 乐观锁，AI 用异步任务，JWT 和服务端资源校验保证安全。

## 0.2 功能实现拆解：是什么、为什么、怎么做

下面每个功能都按面试官最常追问的三个角度展开。回答时可以先说“是什么”，再解释业务上的“为什么”，最后落到接口、状态、数据和异常处理的“怎么做”。

### 0.2.1 登录与 RBAC

**是什么：** 用户登录后获得访问作品、模板、AI 和会员能力的身份；管理员、运营和普通用户拥有不同的页面、按钮与接口权限。

**为什么：** 设计作品、会员订单和 AI 额度都属于用户私有数据，管理端还包含用户启停用、角色调整等敏感操作。只在前端隐藏菜单不能防止用户直接调用接口，所以必须把认证和授权放在服务端。

**怎么实现：**

- 前端 `AuthContext` 保存当前用户和登录态，`PermissionGate` 控制路由或按钮入口。
- Axios 统一加 `Authorization: Bearer`；access token 过期时用 refresh token 刷新，并避免并发请求重复刷新。
- 后端 `JwtAuthFilter` 解析令牌，将用户 ID 和角色写入 `SecurityContext`；`SecurityConfig` 对管理员接口和登录接口配置不同的访问规则。
- `AuthService` 负责密码登录、微信登录接口和手机号验证码接口；密码使用 BCrypt，不保存明文。
- 业务 Service 再做资源归属校验，例如查询或保存作品时附带 `userId`，防止越权。

代码定位：`frontend/src/context/AuthContext.tsx`、`frontend/src/components/auth/PermissionGate.tsx`、`backend/src/main/java/com/chuangkit/admin/security/`、`backend/src/main/java/com/chuangkit/admin/config/SecurityConfig.java`。

### 0.2.2 首页、模板中心、搜索与瀑布流

**是什么：** 首页提供推荐和创作入口，模板中心按分类、关键词和场景查找模板，并以瀑布流展示封面；用户可以收藏、使用模板和查看最近设计。

**为什么：** 模板是降低创作门槛的核心产品资产。搜索和分类帮助用户快速找到合适起点，瀑布流适合海报封面这类比例不一的内容，最近设计则缩短重复进入作品的路径。

**怎么实现：**

- 前端 `HomePage`、`TemplateCenterPage` 和 Masonry 组件负责筛选状态、加载态、空态和卡片操作。
- 后端 `HomeService`、`TemplateService`、`TemplateCenterService` 聚合推荐、分类、搜索和分页数据。
- 用户点击“使用模板”时，服务端复制模板的 Canvas JSON、尺寸和封面创建 `user_design`，不直接修改平台模板。
- 标题、标签、分类、热度等可检索字段放在模板表，画布内部图层仍以 JSON 保存；数据量增大后可接全文索引或搜索引擎。

代码定位：`frontend/src/pages/HomePage.tsx`、`frontend/src/pages/TemplateCenterPage.tsx`、`frontend/src/components/home/`、`backend/src/main/java/com/chuangkit/admin/service/Template*Service.java`。

### 0.2.3 在线编辑器与 Canvas JSON

**是什么：** 编辑器是用户真正完成创作的工作台，当前 MVP 支持文字、图片、形状图层的增删改、撤销重做和 PNG/JPEG 导出。

**为什么：** 如果只做静态预览，用户无法修改模板；如果前后端没有统一的数据协议，模板初始化、自动保存、版本快照和协作会各自维护一套结构，后续很容易不一致。

**怎么实现：**

- 用 `CanvasDocument` 统一描述 `version/width/height/background/layers`，每个图层有稳定 `id`、`type`、位置、尺寸和样式。
- 当前渲染采用 DOM/CSS，编辑状态在 React 中维护；导出时将同一份文档交给 `exportCanvasDocument` 生成图片。
- 作品保存到 `user_design.canvas_json`，模板与用户作品共享协议，模板只读、用户作品可编辑。
- 组件层只负责交互，数据结构和序列化集中管理，便于未来替换 Fabric/Konva 等渲染引擎。

代码定位：`frontend/src/pages/DesignEditorPage.tsx`、`frontend/src/utils/exportCanvasDocument.ts`、`backend/src/main/java/com/chuangkit/admin/service/DesignService.java`。

### 0.2.4 自动保存、版本与冲突提示

**是什么：** 用户编辑后不需要手动频繁点击保存，系统会自动提交；多人或多标签同时修改时，系统能发现版本冲突而不是静默覆盖。

**为什么：** 编辑器操作频繁，逐次请求会造成网络抖动；只在离开页面保存又容易因刷新或崩溃丢数据。多人同时保存时，“最后一次请求覆盖全部内容”会造成不可见的数据丢失。

**怎么实现：**

- 前端变更 `CanvasDocument` 后设置 dirty，900ms 防抖保存，30 秒定时保存兜底，页面离开时用 `keepalive` 尝试提交。
- 请求携带当前 `revision`；后端按 `id + userId + revision` 条件更新，成功才把版本加一。
- 更新影响行数为 0 时返回业务 409；前端保留本地草稿并提示用户加载最新版本，再决定是否重做改动。
- 版本号是最终一致性保护，SSE 或 BroadcastChannel 只是通知远端变更，不能代替数据库乐观锁。

代码定位：`frontend/src/pages/DesignEditorPage.tsx`、`backend/src/main/java/com/chuangkit/admin/service/DesignService.java`、`user_design.canvas_json` 和 `revision` 字段。

### 0.2.5 多人协作与分享

**是什么：** 团队成员可以进入同一设计，看到在线状态、光标、图层锁和文档变化，也可以评论、查看版本快照或通过分享链接只读/编辑。

**为什么：** 运营设计通常不是一个人完成，实时提示可以减少重复编辑和沟通成本；分享链接则适合外部审阅，不必把对方加入完整团队权限。

**怎么实现：**

- 同一浏览器多标签优先使用 `BroadcastChannel`，不支持时监听 `localStorage` 的 storage event。
- 跨客户端通过服务端 SSE，按 `teamId + designId` 组织频道，推送 `cursor`、`document-update`、`layer-lock`、`presence` 等事件。
- `document-update` 以约 120ms 合并，避免拖拽时每个像素都发送一条消息；revision 轮询作为实时链路异常时的兜底。
- 评论、版本快照和分享链接持久化；分享 token 还要校验有效期、撤销状态和 readonly/editable 模式。

**边界：** 当前是事件同步加乐观锁，适合 MVP 和中小规模协作，不是 CRDT/OT 的字符级实时合并；工单中提到的完整历史合并可作为后续演进。

代码定位：`frontend/src/modules/collaboration/`、`backend/src/main/java/com/chuangkit/admin/controller/CollaborationEventController.java`、`backend/src/main/java/com/chuangkit/admin/service/CollaborationEventBroker.java`。

### 0.2.6 AI 图片/视频生成

**是什么：** 用户输入提示词、模式、比例、风格和参考图，系统生成图片、视频或 Agent 结果，并在页面展示任务进度和失败原因。

**为什么：** AI 是降低创作成本的增量能力，但模型调用耗时、会失败、会产生费用，不能让浏览器直接持有密钥或同步等待一个长请求。

**怎么实现：**

- `/admin/ai/generate` 先把用户参数和初始状态写入 `ai_task`，立即返回 `taskId`。
- Java 虚拟线程在后台调用 Provider；前端轮询 `/admin/ai-tasks/{id}`，根据 pending/processing/success/failed 更新 UI。
- Provider 返回的 `outputUrl`、`url`、`b64_json` 等格式在服务端归一为统一结果；密钥只从服务端环境变量读取。
- Provider 未配置、超时或返回异常时，任务明确失败并保存 `errorMsg`，不返回伪造成功结果。

代码定位：`backend/src/main/java/com/chuangkit/admin/service/AiGenerateService.java`、`frontend/src/components/home/AiGenerateResultPanel.tsx`、`frontend/src/api/index.ts`。

### 0.2.7 AI 抠图

**是什么：** 用户上传商品图或人物图，得到透明背景结果，并可对比原图、下载或继续进入编辑器。

**为什么：** 电商和营销设计经常需要把主体从复杂背景中分离。抠图是高频、耗时且依赖外部模型的操作，应复用 AI 任务的可追踪模式。

**怎么实现：**

- 前后端共同校验 JPEG/PNG/GIF 格式和 5MB 大小，先拒绝明显不合法文件。
- 上传后创建异步任务，`MattingProvider` 负责隔离真实 Provider 与开发环境 `MockMattingProvider`。
- 前端轮询任务状态，成功时展示透明图和原图对比，失败支持重试；结果可下载或带入编辑器。

**边界：** 工单中复杂边缘修复、画笔细化等能力在当前代码中未形成完整闭环；真实效果需要配置 Provider 账号后验收。

代码定位：`frontend/src/pages/KoutuEditorPage.tsx`、`frontend/src/components/koutu/KoutuUploadPanel.tsx`、`backend/src/main/java/com/chuangkit/admin/service/MattingService.java`。

### 0.2.8 会员、订购与额度

**是什么：** 用户可以查看会员套餐、创建订单并完成模拟支付；会员获得更高或免基础额度，免费用户按日限制创建、保存和导出。

**为什么：** 会员是平台商业化入口，额度是成本控制和防滥用边界。额度必须由服务端判断，否则用户绕过前端按钮就能无限调用接口。

**怎么实现：**

- `MemberService` 查询套餐和当前等级，`MemberCheckoutService` 创建订单并轮询支付状态。
- 支付完成后更新会员等级；`UsageQuotaService` 按 `user_id + usage_date` 维护每日用量，创建、保存、导出分别计数。
- 数据库唯一约束避免同一用户同一天产生重复用量记录，Service 在创建作品、保存和导出前执行额度校验。
- 当前会员权益主要按 `memberLevel` 判断；生产可进一步按 SKU、有效期、退款和幂等支付回调配置。

代码定位：`frontend/src/components/membership/MembershipModal.tsx`、`frontend/src/pages/VipPage.tsx`、`backend/src/main/java/com/chuangkit/admin/service/Member*Service.java`、`UsageQuotaService.java`。

### 0.2.9 客服工单

**是什么：** 用户从右下角帮助入口提交问题，查看自己的工单、优先级、状态和客服回复。

**为什么：** 在线设计平台会遇到登录、模板、导出和会员支付问题。工单能形成可追踪的服务闭环，比只放一个联系方式更容易统计和分派。

**怎么实现：**

- `HelpFab` 打开客服二维码或工单入口；用户提交内容后由后端写入 `support_ticket`。
- `SupportTicketService` 限制用户只能查看和操作自己的工单，支持优先级、状态流转和回复字段。
- 管理端可以围绕工单状态进行处理；当前代码没有证据证明已完成 WebSocket 实时 IM、音视频、文件传输或完整 AI 客服切换。

代码定位：`frontend/src/components/layout/HelpFab.tsx`、`frontend/src/pages/SupportTicketPage.tsx`、`backend/src/main/java/com/chuangkit/admin/service/SupportTicketService.java`。

### 0.2.10 虚拟列表与虚拟网格

**是什么：** 只渲染当前视口附近的数据项，适合模板瀑布流、用户列表等可能有几百或几千条数据的页面。

**为什么：** 一次性渲染全部卡片会增加 DOM 数量、图片布局和滚动计算，页面容易卡顿；虚拟化能把渲染量控制在“可视区域 + overscan”。

**怎么实现：**

- 定高列表根据 `scrollTop / itemHeight` 计算起止索引；不定高列表用 `ResizeObserver` 测量真实高度。
- 使用 spacer 保留完整滚动高度，只挂载可视区元素；滚动更新用 `requestAnimationFrame` 节流。
- 接近列表尾部时触发 `loadMore`；`VirtualGrid` 根据容器宽度计算列数和行高。

代码定位：`frontend/src/components/common/VirtualList.tsx`、`frontend/src/components/common/VirtualGrid.tsx`、`frontend/src/utils/virtualListMath.mjs`。

### 0.2.11 管理端与 Java 接口规范

**是什么：** `admin-web` 是面向运营和管理员的 ToB 端，后端以 `/admin` 为统一接口前缀，提供用户、角色和业务管理能力。

**为什么：** ToC 创作页面和 ToB 运营页面的交互密度、权限模型和组件习惯不同，拆开可以降低相互影响；统一接口规范则减少前后端联调成本。

**怎么实现：**

- 管理端使用 Vue 3 + Element Plus + Vite，提供用户列表、角色调整、账号启停用和管理员登录。
- 后端按 Controller/Service/Mapper 分层，统一返回 `code/message/data`；参数使用 Jakarta Validation。
- `GlobalExceptionHandler` 统一处理参数校验、业务异常和未知异常，避免每个 Controller 重复写 try/catch。
- SpringDoc 提供 `/admin/swagger-ui.html`，方便接口查看和在线测试；认证和角色规则由 Spring Security 集中配置。

代码定位：`admin-web/src/App.vue`、`backend/src/main/java/com/chuangkit/admin/common/Result.java`、`GlobalExceptionHandler.java`、`backend/src/main/resources/application.yml`。

### 0.2.12 MCP、Skills 与工程化能力

**是什么：** MCP 服务和 Skills 是开发、审查、数据排查与协作流程的工具，不是普通用户在设计页面上直接点击的业务功能。

**为什么：** 项目同时包含前端、后端、数据库和多种 AI 能力，重复查库、审查和写日报会降低交付效率；工具化可以把安全边界和团队规范固化下来。

**怎么实现：**

- MySQL MCP 通过 stdio 提供健康检查、列举表、描述表和查询；默认只读，写入/DDL 必须开启环境变量并显式确认，查询参数化且限制行数。
- Code Review Skill 支持 changed-files、组件规范、性能、类型契约等规则，输出文件、行号、严重等级和建议；编辑后 Hook、提交前/后复核形成自动触发链路。
- 日报 Skill 把当天变更按工作项、风险和下一步整理；Figma MCP 主要用于设计稿理解和开发辅助，交付记录已明确其使用边界。
- 这些检查不能替代 TypeScript 编译、Lint、单元测试和接口回归，Hook 是否执行还取决于编辑器和 Git 配置。

代码定位：`.cursor/mcp.json`、`mcp/mysql-server/`、`cursor-skills/code-review/`、`.cursor/skills/`、`scripts/codex-code-review.mjs`、`.codex/skills/daily-report-summary/`。

## 0.3 交互与页面效果：怎么实现、在哪里实现

这一节回答“页面上看到的效果到底是怎么做出来的”。不要只说“用了 React 或 CSS”，而应按“事件触发 -> React 状态变化 -> DOM/CSS 渲染 -> 必要时调用接口”来回答。

### 0.3.1 编辑器画布自适应、缩放和参考线

**看到的效果：** 作品画布能随着工作区大小自动适应；用户可点击放大、缩小、1:1 和适应屏幕。打开参考线后，画布上会出现网格。

**怎么实现：**

1. `DesignEditorPage` 保存 `scale` 和 `zoomMode` 状态。
2. `ResizeObserver` 监听画布容器尺寸，在 fit 模式中按“可用宽度/画布宽度”和“可用高度/画布高度”计算较小的缩放比例。
3. 外层 `canvas-frame` 使用 `document.width * scale` 和 `document.height * scale` 预留正确空间，内层画布使用 `transform: scale(scale)`、`transform-origin: top left` 做视觉缩放，所以坐标体系仍保持原始画布大小。
4. 参考线不是额外渲染大量 DOM，而是给画布加 `has-guides` 类名，再通过 `::after` 的两组 `linear-gradient` 画 40px 网格。

**在哪里实现：**

- 交互和缩放计算：`frontend/src/pages/DesignEditorPage.tsx` 中 `ResizeObserver`、`setZoom`、`fitCanvas` 以及画布 `transform`。
- 画布、网格和缩放样式：`frontend/src/index.css` 中 `.design-editor-canvas-frame`、`.design-editor-canvas`、`.design-editor-canvas.has-guides::after`。

**面试说法：** “我没有因为缩放就改写所有图层坐标，而是保留原始设计坐标，统一由 CSS transform 缩放；拖拽时再除以 scale 还原成设计坐标，因此不同缩放倍数下操作不会漂移。”

### 0.3.2 图层选中、拖拽和四角缩放

**看到的效果：** 点击图层出现蓝色选中框，拖拽可移动文字、图片或形状；四个角的控制点可以改变宽高，图层不会被拖出画布边界。

**怎么实现：**

1. 每个图层以绝对定位元素渲染，`left/top/width/height` 来自 `CanvasDocument.layers`。
2. 鼠标或触摸开始时通过 `onPointerDown` 记录起点、原始文档和当前缩放比例到 `dragRef` 或 `resizeRef`，并调用 `setPointerCapture`，保证指针移出元素后仍能持续接收事件。
3. 移动时计算 `(clientX - startX) / scale` 和 `(clientY - startY) / scale`，把屏幕位移换算为画布位移；再用 `Math.max/Math.min` 限制图层位置和最小尺寸。
4. 结束时把变更前文档压入 `past` 历史栈、清空 `future`，因此撤销/重做的是完整文档快照；选中状态通过 `selectedLayerId` 叠加 CSS outline 和四个缩放手柄。

**在哪里实现：**

- 指针事件、边界计算和历史栈：`frontend/src/pages/DesignEditorPage.tsx` 的 `onLayerPointerDown`、`onLayerPointerMove`、`onLayerPointerUp`、`onResizePointerDown`。
- 图层绝对定位、选中框、鼠标样式和四角手柄：`frontend/src/index.css` 中 `.design-editor-layer`、`.is-selected`、`.design-editor-resize-handle`。

**面试说法：** “这个编辑器当前是 DOM/CSS 图层渲染，拖拽不是依赖浏览器的原生 drag 事件，而是 Pointer Events 加坐标换算。这样鼠标和触摸操作可以复用同一条逻辑，也能在缩放状态下保持准确。”

### 0.3.3 自动保存、保存状态和远端更新提示

**看到的效果：** 用户编辑后顶部显示“保存中/已保存/保存失败/版本冲突”；短暂停止操作后自动保存。其他成员更新作品时出现横幅，用户可以加载最新版本或稍后处理。

**怎么实现：**

1. 图层变更后将 `dirty` 置为 true，`saveState` 置为 saving/saved/error/conflict 之一，视图根据状态渲染不同文字与颜色。
2. `useEffect` 用 900ms `setTimeout` 做防抖，另一个 effect 用 30 秒 `setInterval` 做兜底；离开页面时以 `fetch(..., { keepalive: true })` 尝试保存最后一份脏数据。
3. 保存时提交 `revision`。后端按作品 ID、用户 ID 和 revision 条件更新，更新不到记录时返回 409；前端不覆盖本地草稿，转为 conflict 状态。
4. 协作事件或 revision 轮询发现远端版本升高后设置 `remoteUpdateAvailable`，条件渲染更新横幅；点击后重新拉取并用服务端文档重置本地状态。

**在哪里实现：**

- 保存流程、冲突和横幅操作：`frontend/src/pages/DesignEditorPage.tsx` 的 `saveDesign`、定时 effect、`reloadLatestDesign`。
- 顶部状态和横幅样式：`frontend/src/index.css` 中 `.design-editor-save-state`、`.design-editor-remote-update-banner`。
- 最终 revision 条件更新：`backend/src/main/java/com/chuangkit/admin/service/DesignService.java`。

### 0.3.4 协作光标、图层锁和成员在线状态

**看到的效果：** 多个用户编辑同一作品时，可以看到彩色姓名光标；图层被他人编辑时显示“由某人编辑”，并阻止本地继续拖动；协作面板显示在线、离开、离线。

**怎么实现：**

1. 编辑器鼠标移动时每 40ms 最多发送一次 cursor 事件，减少高频移动带来的事件数量。
2. 开始拖动或缩放时发布 `layer-lock`，结束时发布 `layer-unlock`；若本地图层锁属于别人，就直接停止交互并提示。
3. `collaborationBridge` 同浏览器优先使用 `BroadcastChannel`，不支持时回退 `localStorage` storage event；跨客户端用 HTTP 建立 SSE 读取流并用 POST 上报事件。
4. 文档更新在 bridge 内合并为约 120ms 一次；`CollaborationCanvasSignals` 根据收到的光标和锁状态渲染绝对定位的光标标记和锁标签。

**在哪里实现：**

- 编辑器发布事件、维护远端状态：`frontend/src/pages/DesignEditorPage.tsx`。
- 通道选择、SSE 读取、120ms 合并：`frontend/src/modules/collaboration/collaborationBridge.ts`。
- 光标和锁标签的 React 渲染：`frontend/src/modules/collaboration/CollaborationCanvasSignals.tsx`。
- 光标三角形、姓名标签和锁标签的视觉样式：`frontend/src/index.css` 中 `.design-editor-remote-cursor`、`.design-editor-layer-lock`。

**边界：** 这套机制让用户“看得到”对方动作并减少冲突，但最后落库仍依赖 revision 乐观锁；它不是按字符或操作自动合并的 CRDT/OT。

### 0.3.5 导出图片效果

**看到的效果：** 点击下载可以导出 PNG/JPEG，并可选择 1x 到 4x 分辨率和 JPEG 质量；导出结果与当前画布的文字、图片、形状和透明度保持一致。

**怎么实现：**

1. 导出前先调用 `usageApi.consume('export')` 扣减或校验额度。
2. `clampExportOptions` 将格式、倍率和质量限制在安全范围，防止过大的 Canvas 占用过多内存。
3. `renderDocumentToDataUrl` 创建离屏 Canvas，先绘制背景，再按图层顺序绘制文字、圆形/矩形和图片，并设置 `globalAlpha` 处理透明度。
4. 生成 Data URL 后创建临时 `<a>` 元素并触发 download，无需把图片先上传到服务端。

**在哪里实现：**

- 下载菜单和导出入口：`frontend/src/pages/DesignEditorPage.tsx` 的 `exportDesign`。
- Canvas 绘制、图片加载和编码：`frontend/src/utils/exportCanvasDocument.ts`。

### 0.3.6 AI 生成的弹窗、加载和结果展示

**看到的效果：** 提交 AI 后弹窗显示转圈加载，完成后自动换成图片或视频，失败时显示可解释错误；结果可以下载。

**怎么实现：**

1. 创建任务接口先返回 taskId，前端面板以 `status=0` 呈现 pending 状态。
2. 面板每 1.5 秒请求一次任务详情，任务成功或失败后停止轮询，并根据状态切换 loading、error、image/video 三套区域。
3. loading 图标由 Lucide 的 `Loader2` 加 `animate-spin` 实现；弹窗淡入和背景模糊由 Tailwind 的 `animate-fade-in`、`backdrop-blur-sm` 和遮罩类实现。
4. 成功结果直接使用 `<img>` 或 `<video controls>`，下载按钮链接到服务端记录的 outputUrl。

**在哪里实现：** `frontend/src/components/home/AiGenerateResultPanel.tsx`；任务异步创建和状态写入在 `backend/src/main/java/com/chuangkit/admin/service/AiGenerateService.java`。

### 0.3.7 AI 抠图的透明背景、对比、进度和重试

**看到的效果：** 上传后先出现本地原图预览和处理中遮罩；完成后左右并排展示原图与透明图，透明区域显示棋盘格；用户可切换回原图、下载透明图、重试或继续编辑。

**怎么实现：**

1. 选择文件后立即通过 `URL.createObjectURL` 建立本地预览占位任务，用户不必等待网络上传完成才能看到卡片。
2. `removePersonBackground` 按需加载浏览器端 Selfie Segmentation 模型，在 Canvas 中绘制原图和分割 mask，并通过 `globalCompositeOperation = 'destination-in'` 输出透明 PNG；之后再上传并创建可轮询的抠图任务。
3. 页面每 1.5 秒刷新 pending 任务。成功时读取 outputUrl，失败时保留文件或地址用于重试；“继续编辑”将透明图 URL 传到新建编辑器路由。
4. 原图/结果采用两列 CSS Grid。结果区域的棋盘格由四层 `linear-gradient` 背景实现；处理中覆盖半透明状态层，进度条用 `@keyframes koutu-progress` 来回移动，而不是伪造真实进度百分比。

**在哪里实现：**

- 上传占位、轮询、前后对比和按钮逻辑：`frontend/src/pages/KoutuEditorPage.tsx`。
- 浏览器端人物分割和透明 PNG：`frontend/src/utils/localPersonCutout.ts`。
- 卡片、棋盘格、进度条动画和状态遮罩：`frontend/src/styles/koutu-editor.css`。
- 服务端任务与 Provider 边界：`backend/src/main/java/com/chuangkit/admin/service/MattingService.java`。

**注意：** 进度条表达“正在处理”，不是模型真实百分比；开发环境若标识“本地演示结果”，说明走的是 Mock Provider，不能把该结果包装成真实云端模型效果。

### 0.3.8 模板瀑布流、图片懒加载和卡片悬停

**看到的效果：** 模板封面按不同高度错落排列，窗口变窄时列数自动减少；卡片悬停时有阴影和轻微放大；模板中心初次加载时显示骨架屏。

**怎么实现：**

1. 瀑布流使用 CSS Multi-column：`columns-2` 到 `xl:columns-6` 控制响应式列数，每张卡片用 `break-inside-avoid` 避免被拆到两列。
2. 模板封面使用数据库宽高形成 `aspect-ratio`，图片使用 `loading="lazy"`，减少首屏图片压力。
3. Hover 效果由 Tailwind 的 `transition`、`group-hover:scale-[1.02]`、`hover:shadow` 完成，未引入额外动画库。
4. 加载态按照预设高度渲染多个 `animate-pulse` 占位块，避免数据到达前页面布局突然跳动。

**在哪里实现：**

- 首页模板瀑布流：`frontend/src/components/home/MasonryFeed.tsx`。
- 模板中心瀑布流、懒加载、悬停和骨架屏：`frontend/src/components/template-center/TemplateCenterMasonry.tsx`。
- 页面接入位置：`frontend/src/pages/TemplateCenterPage.tsx`。

### 0.3.9 虚拟列表/网格的滚动性能效果

**看到的效果：** 作品或收藏很多时，页面滚动仍然稳定；用户视觉上仍能滚到完整列表底部，接近底部时自动加载更多。

**怎么实现：**

1. 容器根据 `scrollTop`、可视高度和 overscan 算出起止索引，只对 `items.slice(start, end)` 渲染真实卡片。
2. 用与完整数据高度相同的 spacer 占位，并让可见项绝对定位在其真实 top 位置，所以滚动条长度和用户感知仍与完整列表一致。
3. 不定高列表和网格用 `ResizeObserver` 测量卡片或行高，并更新 offsets；滚动状态更新用 `requestAnimationFrame` 节流。
4. 滚动到阈值附近时用 `shouldLoadNextPage` 触发 `onNearEnd`，而不是在每个 item 上挂监听器。

**在哪里实现：**

- 通用实现：`frontend/src/components/common/VirtualList.tsx`、`frontend/src/components/common/VirtualGrid.tsx`、`frontend/src/utils/virtualListMath.mjs`。
- 作品和收藏页面的接入：`frontend/src/components/my-design/MyDesignGrid.tsx`、`frontend/src/components/my-design/MyFavoriteGrid.tsx`。
- 占位容器和绝对定位样式：`frontend/src/index.css` 中 `.virtual-list`、`.virtual-grid`、`.virtual-list__spacer`、`.virtual-grid__row`。

### 0.3.10 讲“效果实现”时的通用回答模板

> 这个效果我会先区分它是纯前端视觉效果，还是需要后端状态支撑的业务效果。以编辑器拖拽为例，纯交互部分是 Pointer Events 记录起点、按当前缩放换算坐标，再用 React state 更新图层和 CSS 绝对定位渲染；但自动保存、协作提示和冲突处理会继续调用后端接口，最终以 revision 保证数据不被覆盖。这样既能说清 UI 怎么动，也能说清真实数据怎样保持一致。

## 1. 项目是什么

**灵图工坊**是一个面向运营、电商和普通创作者的在线低代码设计平台，业务形态接近创客贴/Canva。用户可以搜索模板或选择场景，新建一张设计，在浏览器内编辑文字、图片和形状，自动保存并导出图片；项目同时覆盖 AI 创作、图片抠图、团队协作、分享、会员额度和用户中心等闭环能力。

它不是单纯的静态官网复刻。页面数据、账号、模板、作品画布、AI 任务和团队协作数据都由后端接口与数据库支撑，刷新后仍可恢复。

### 1 分钟口述版

> 我做的是一个在线低代码设计平台，核心目标是降低非设计人员制作海报、营销图和内容素材的门槛。用户可以从首页或模板中心检索模板，也可以从场景创建空白设计；进入编辑器后，对文字、图片和形状图层做编辑，系统将画布保存为 JSON，并支持自动保存和 PNG/JPEG 导出。
>
> 技术上，前端采用 React 19、TypeScript、Vite、Tailwind CSS、TanStack Query 和 Axios；后端采用 Java 21、Spring Boot 3、MyBatis-Plus、Spring Security、JWT，开发环境使用 H2，生产环境可切换 MySQL。重点处理了编辑器的画布序列化、乐观锁冲突、异步 AI 任务、团队协作事件和数据权限。比如两个用户同时保存同一作品时，后端通过 revision 条件更新避免后提交覆盖先提交，前端会提示用户加载最新版本。

### 3 分钟口述版

> 这个项目是灵图工坊，一个在线低代码设计平台。它服务的主要是没有专业设计能力、但需要高频制作海报、电商素材和活动内容的用户。完整链路是：用户登录后在首页或模板中心搜索模板，基于模板或指定尺寸创建作品，进入编辑器调整图层，作品会自动保存到个人空间，最后导出或通过分享链接协作。
>
> 前端使用 React 19 和 TypeScript。页面数据用 TanStack Query 管理请求、缓存和加载状态，Axios 统一处理请求头、统一响应格式以及 JWT 刷新。编辑器没有把画布拆成多张业务表，而是定义了包含宽高和 layers 的 CanvasDocument，把它序列化成 canvasJson 存在 user_design 表中。这样模板初始化、编辑器恢复、自动保存和版本快照共用同一份数据协议，迭代成本更低。
>
> 后端按 Controller、Service、Mapper 分层。Spring Security 将公开资源、登录资源、普通登录资源和管理员资源分开；JWT Filter 解析令牌后把用户 ID 和角色放到 SecurityContext，Service 层还会做作品归属校验，不能只相信前端传来的设计 ID。保存作品时带 revision：后端用 `id + revision + userId` 作为更新条件，更新成功才把 revision 加一，因此能阻止并发覆盖。前端采用短防抖保存、定时兜底保存和离开页面前 keepalive 保存，并在冲突时保留本地草稿、提示用户重新加载。
>
> AI 模块采用“创建任务后异步执行”的模式。接口先落库 ai_task 并返回 taskId，后台虚拟线程调用 Provider，前端轮询任务状态。没有配置真实 Provider 时，任务会显式失败并返回原因，不用假图片掩盖集成问题。团队协作方面，前端在同浏览器多标签使用 BroadcastChannel，在跨客户端时使用服务端 SSE 事件；同时保留 revision 轮询和版本快照，避免实时通道异常影响核心保存。

## 3. 核心业务流程

### 3.1 模板创作主流程

```text
登录/注册
  -> 首页/模板中心浏览、搜索和筛选
  -> 选择模板或输入自定义尺寸
  -> POST /admin/designs 创建 user_design
  -> 进入 /editor/{id}，加载 canvasJson
  -> 编辑图层，前端标记 dirty
  -> 防抖自动保存 / 定时兜底保存
  -> 后端校验用户、额度和 revision 后写入数据库
  -> 导出 PNG/JPEG 或创建分享链接
```

可这样讲：

> 我把“模板”和“用户作品”分开设计。模板是平台资产，用户点击使用模板时并不修改原模板，而是复制模板的画布 JSON、尺寸和封面到 user_design，后续修改只落到用户自己的作品中。这既保护了模板数据，也让用户作品可以独立保存、删除和分享。

### 3.2 编辑保存与冲突处理流程

```text
用户修改图层
  -> 本地 document 更新，dirty = true
  -> 900ms 防抖触发保存；30s 定时保存作兜底
  -> PUT /admin/designs/{id}，携带 canvasJson 和 revision
  -> 后端按 id + userId + revision 条件更新
      -> 更新成功：revision + 1，前端清除 dirty
      -> 更新 0 行：返回 409，前端保留本地草稿并提示冲突
  -> 用户可重新加载服务端最新版本，再决定是否继续编辑
```

这是一个很重要的面试点：项目没有采用“最后一次保存永远覆盖”的做法，而是在资源表上维护版本号，利用**乐观锁**避免静默丢数据。

### 3.3 AI 生成流程

```text
已登录用户提交 prompt、模式、比例、风格和参考图
  -> POST /admin/ai/generate
  -> 立即创建 ai_task，状态为 processing/pending
  -> 立即返回 taskId 给前端
  -> 后端虚拟线程调用外部 AI Provider
      -> 成功：写 outputUrl、完成时间、成功状态
      -> 失败：写 errorMsg、完成时间、失败状态
  -> 前端 GET /admin/ai-tasks/{id} 轮询
  -> 展示图片、视频或失败原因
```

### 3.4 图片抠图流程

```text
选择图片
  -> 前后端限制 JPEG/PNG/GIF 且不超过 5 MB
  -> 上传到服务端
  -> 创建抠图任务并轮询
  -> MattingProvider 执行真实服务或开发环境 Mock
  -> 返回透明背景图，可下载或继续进入编辑器
```

### 3.5 团队协作流程

```text
用户进入编辑器
  -> 获取当前团队和成员状态
  -> 心跳上报在线状态
```

## 5. 关键数据模型

### 5.1 为什么使用 Canvas JSON

作品的核心数据不是固定字段，而是不断变化的图层列表。当前画布结构可以抽象为：

```json
{
  "version": "1.0",
  "width": 1242,
  "height": 1660,
  "layers": [
    {
      "id": "layer-1",
      "type": "text",
      "content": "夏日促销",
      "x": 100,
      "y": 160,
      "fontSize": 48,
      "color": "#111111"
    },
    {
      "id": "layer-2",
      "type": "image",
      "src": "https://...",
      "x": 0,
      "y": 0,
      "width": 1242,
      "height": 720
    }
  ]
}
```

`user_design` 中保存 `canvas_json`、宽高、封面、状态和 `revision`。这种做法的优点是：

- 图层类型扩展时不必频繁改表；
- 模板初始化和用户作品恢复共用同一数据结构；
- 版本快照可以直接保存当时的画布 JSON；
- 前端可以把编辑器状态与后端持久化模型清晰分离。

代价是不能直接通过关系型字段检索图层内部内容。当前项目把模板标题、标签、分类等可检索字段独立放在模板表；如果以后要做“按画布内文字搜索”，可引入异步索引、全文检索或将关键字段冗余到专用索引表。

### 5.2 主要表关系

```text
sys_user 1 --- n user_design
design_template 1 --- n user_design（从模板创建时保留 template_id）
sys_user 1 --- n ai_task
sys_user 1 --- n user_usage_daily
```

## 7. 重难点与实现方式

### 难点一：编辑器状态与持久化的一致性

**问题：** 设计画布包含多种图层、位置和样式。编辑操作频繁，如果每一步都立即请求后端，网络开销大且容易乱序；如果只在离开页面时保存，异常关闭又会丢内容。

**实现：**

1. 前端以 `CanvasDocument` 保存当前画布，变更时设置 `dirty`。
2. 维护 `past/future` 两个历史栈，支持撤销和重做。
3. 首次变更后 900 ms 防抖保存，另外每 30 秒做一次兜底保存。
4. 离开页面时通过 `fetch(..., { keepalive: true })` 尝试提交最后一份脏数据。
5. 后端保存时同时校验作品归属、会员额度和版本号，成功后版本递增。

**收益：** 编辑体验流畅，同时把网络请求控制在合理范围，并降低意外退出导致的数据丢失概率。

### 难点二：多人并发保存不能覆盖彼此

**问题：** 两个用户都读取了 revision=5 的作品，A 保存后变为 6，B 如果继续无条件覆盖，会把 A 的改动静默丢掉。

**实现：**

```sql
UPDATE user_design
SET canvas_json = ?, revision = revision + 1
WHERE id = ? AND user_id = ? AND revision = ?;
```

业务层只有在影响行数为 1 时才认为成功；若为 0，返回业务码 `409`。前端识别冲突后停止自动覆盖，保留本地草稿并提供“重新加载最新版本”的明确操作。协作事件用于提高实时性，但真正的数据正确性依然以数据库 revision 为准。

**面试要点：** SSE、广播通道只能做“通知”，不能替代数据库的并发控制；最终一致性要落在服务端条件更新上。

### 难点三：AI 调用耗时且结果不确定

**问题：** 外部模型调用可能持续数秒甚至更久，不能让 HTTP 请求一直阻塞；Provider 也会超时、限流或返回异常格式。

**实现：**

1. 先将输入参数、用户 ID、工具 ID 和初始状态写入 `ai_task`。
2. 同步接口立即返回 `taskId`，前端进入轮询状态。
3. 后端在 Java 虚拟线程中调用 Provider；密钥只从服务端环境变量或服务端配置读取。
4. 成功时保存 `outputUrl`，失败时保存截断后的 `errorMsg` 和结束时间。
5. AI Provider 未配置时任务明确失败，而不是返回伪造的成功图片。

**后续演进：** 生产环境可把进程内异步替换为消息队列 + Worker，并增加重试策略、回调验签、任务超时回收、速率限制和指标监控。

### 难点四：协作既要实时，也要可恢复

**问题：** 协作者希望看到光标、锁定和别人正在修改的内容，但 Web 实时连接会断开，且仅靠实时消息无法审计历史。

**实现：**

- 同一浏览器不同标签通过 `BroadcastChannel` 通信，不支持时降级 `localStorage` 事件。
- 跨客户端通过 `SseEmitter` 按 `teamId + designId` 维度广播事件。
- 画布更新事件以 120 ms 合并发送，减少拖拽时的事件洪泛。
- 图层锁用于表达正在编辑，防止 UI 上产生误操作。
- 评论、在线状态和版本快照使用数据库持久化；编辑器还每 15 秒检查远端 revision 作为实时链路失效后的兜底。

**边界：** 当前实现更适合中小规模协作和 MVP 验证，不是 OT/CRDT 级别的字符级强协同编辑。若要做大型实时协作，应引入 WebSocket 集群、Redis Pub/Sub、操作日志及 CRDT/OT 冲突合并策略。

### 难点五：认证、授权和数据归属不能只做前端拦截

**问题：** 仅隐藏页面或按钮无法阻止用户直接调用接口读取/修改其他人的作品。

**实现：**

- 登录使用 BCrypt 校验密码，服务端签发 access token 与 refresh token。
- Axios 在请求中追加 `Authorization: Bearer <token>`；401 时用 refresh token 串行刷新，避免多个请求并发刷新令牌。
- `JwtAuthFilter` 将用户 ID 和角色写入 Spring Security 上下文。
- SecurityConfig 限制管理员 AI 配置等敏感路径，普通用户资源要求登录。
- `DesignService.getById` 和保存逻辑校验 `user_design.user_id`；团队协作再验证设计归属当前团队。
- 分享链接使用独立 token，并区分只读与可编辑模式及有效期/撤销状态。

### 难点六：免费额度必须由服务端强制

**问题：** 如果额度只靠前端按钮置灰，用户可以绕过页面直接调用创建、保存和导出接口。

**实现：** `UsageQuotaService` 在服务端按 `user_id + usage_date` 查询或创建每日记录，免费用户创建、保存、导出各自每天最多一次；会员等级大于 0 时跳过额度限制。数据库在 `(user_id, usage_date)` 上有唯一约束，避免同一天出现重复额度记录。

**可改进点：** 当前的“查询后更新”在极高并发下可以继续收紧为原子 SQL 更新或悲观锁；套餐也可从简单的 `memberLevel > 0` 演进为按 SKU 配置差异化权益。

## 9. 面试官高频问题与参考回答

### Q1：为什么不用 Fabric.js、Konva 或 Canvas API，而是自己维护画布 JSON？

> 这里要区分“画布渲染引擎”和“持久化协议”。本项目当前编辑器 MVP 使用 DOM/CSS 实现图层交互，并用 CanvasDocument JSON 作为统一的作品协议。JSON 不是替代渲染库，而是为了让模板、保存、版本与协作都能交换同一份数据。若产品要支持大量对象、自由旋转、滤镜、复杂路径或高性能缩放，我会评估 Fabric.js/Konva；但即便换渲染引擎，后端仍应持久化可版本化的领域 JSON，而不应直接存浏览器运行时对象。

### Q2：为什么保存时要传 revision？只用 updateTime 不行吗？

> revision 是明确的并发版本号。客户端读取到 revision=5 后提交保存，服务端只有在数据库仍为 5 时才允许更新并加一。updateTime 依赖时间精度，表达语义不够直接，也可能因为时钟与精度产生边界问题。revision 更适合作为乐观锁条件，冲突时可稳定返回 409，让前端做可见的冲突处理。

### Q3：乐观锁冲突以后为什么不自动合并？

> 自动合并取决于操作粒度。当前保存单位是一整份 canvasJson，直接合并可能把两个用户改同一图层的结果合成错误内容，所以先选择保守策略：不覆盖、保留草稿、让用户加载最新版本。后续如果要更进一步，会把图层操作建模成 add/update/delete operation，再按 layerId 合并；若要做文字级协作，则考虑 CRDT/OT。

### Q4：为什么协作使用 SSE，而不是 WebSocket？

> 当前协作以服务端向客户端广播为主，客户端上报事件仍可以走普通 HTTP POST；SSE 实现简单、自动重连语义清晰，适合 MVP 和中小并发场景。将来如果需要高频双向实时操作、房间广播、消息确认或更高连接密度，再升级 WebSocket，并搭配 Redis 做跨实例事件分发。无论用哪种实时协议，revision 乐观锁都应保留作为最终写入保护。

### Q5：AI 生成为什么要异步？为什么不让前端直接调用模型？

> AI 推理耗时不可控，异步任务避免浏览器请求长时间阻塞，也能把进度、失败原因和结果归属持久化。前端直连模型会暴露 API Key，难以做额度、审计、内容安全和 Provider 切换，因此调用必须经过后端。当前服务端保留 Provider 配置边界，密钥来自环境变量，不进入前端包。

### Q6：AI Provider 返回的 JSON 不同，怎么兼容？

> 当前服务兼容 `outputUrl`、`url` 以及 OpenAI 风格 `data[0].url/b64_json` 这类输出，并把结果归一为 outputUrl。更成熟的方案会把每家 Provider 都封装成独立适配器，由统一接口返回标准 TaskResult，而不是让控制器或前端理解厂商响应。

### Q7：JWT 放在 localStorage 有什么风险？怎么改进？

> localStorage 方案实现简单，便于当前 SPA 的请求拦截器注入，但它会受到 XSS 风险影响。生产环境更稳妥的方式是将 refresh token 放在 HttpOnly、Secure、SameSite Cookie，access token 采用短时内存令牌，同时配合 CSP、严格的富文本清洗、令牌轮换和登出失效机制。本项目已经有 access/refresh 分离和刷新串行化，Cookie 化是下一步安全增强。

### Q8：怎么防止用户越权访问别人的作品？

> 不能只靠前端路由。后端先由 Security Filter 从 JWT 得到当前用户，再在 Service 层查作品并比较 `design.userId` 和当前 userId；保存 SQL 也会附带 userId 条件。团队协作会进一步验证设计所有者属于当前团队；分享场景只有有效且未撤销的 token 才可访问，并按 readonly/editable 限制操作。

### Q9：免费额度如何防刷？

> 当前版本已经把校验放在服务端，而非前端。使用 `(user_id, usage_date)` 唯一记录每天三类动作的用量，超限返回 429。进一步可以加入原子扣减、分布式限流、手机号/设备风控、幂等键和支付权益的服务端签名校验；对于 AI 任务，还要在创建任务前预扣额度，在确定失败时按业务规则返还。

### Q10：开发为什么用 H2，生产为什么用 MySQL？

> H2 让新开发者不依赖外部数据库即可启动、跑测试和演示；项目 schema 使用接近 MySQL 的语法并且生产 profile 切换到 MySQL。上线前我会在 MySQL 做完整迁移演练，检查方言差异、索引、事务隔离级别和数据量下的分页性能，不能因为 H2 可跑就假设生产数据库没有问题。

### Q11：TanStack Query 和 Context 各自解决什么？

> TanStack Query 管理“服务端状态”，例如模板列表、用户作品和协作数据，负责请求、缓存、失效和刷新；Context 管理跨页面的 UI 或会话状态，例如登录用户、创建弹窗、会员弹窗。这样避免把服务端数据全部塞进 Context，减少手写 loading/error/cache 逻辑。

### Q12：搜索接口如何保证性能？

> 当前模板搜索按标题和标签做条件查询，列表使用分页。数据量扩大后，`LIKE '%keyword%'` 可能无法充分命中普通索引，因此我会根据搜索需求引入全文索引或 Elasticsearch；同时限制 pageSize、建立分类/状态/热度的组合索引，热点结果加缓存，并用搜索日志优化同义词和排序策略。

### Q13：哪些地方还不够生产化？

> 我会主动说明边界：协作目前是事件同步加版本保护，并非 CRDT；AI 任务现在采用进程内异步，生产应迁到队列和 Worker；上传需要进一步接对象存储、病毒扫描和 CDN；CORS 不能长期放开为全域；会员权益要从简单等级判断升级为可配置套餐；还应补充链路监控、审计日志、压测和灾备方案。说明这些不是否定项目，而是能清楚识别 MVP 到生产系统的演进路径。
