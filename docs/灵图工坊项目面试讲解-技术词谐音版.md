# 灵图工坊项目面试讲解：技术词谐音记忆版

> 用途：面试前朗读和记忆英文技术词。
>
> 说明：括号内是中文近似读音，不是正式翻译，也不是技术实现本身。面试时先读英文，再说中文含义，例如“React（瑞爱科特），用于构建前端交互界面”。完整实现和代码定位请看《灵图工坊项目面试讲解.md》。

## 1. 30 秒介绍

> 这是一个在线低代码设计平台，面向运营、电商和普通创作者。用户可以搜索模板，进入编辑器修改文字、图片和形状，自动保存并导出图片；还支持 AI 生成、AI 抠图、团队协作、会员额度和管理端。
>
> 前端使用 React（瑞爱科特）+ TypeScript（泰普斯可瑞普特）+ Vite（外特），后端使用 Spring Boot（斯普林布特）+ Java（加瓦）。作品用 Canvas JSON（看挖死 杰森）保存；多人同时保存时使用 revision（瑞威申）乐观锁，AI 使用异步任务，登录通过 JWT（杰威提）和 RBAC（阿尔巴克）保证权限安全。

## 3. 功能怎么讲：是什么、为什么、怎么做

### 3.1 登录和权限

> **是什么：** 用户登录后才能访问个人作品、AI 和会员；管理员、运营和普通用户看到的能力不同。
>
> **为什么：** 作品和订单属于私有数据，不能只靠前端隐藏按钮。
>
> **怎么做：** 前端 React（瑞爱科特）通过 Axios（艾克西欧斯）给请求加 JWT（杰威提）；后端 Spring Security（斯普林 西克尤瑞提）解析令牌，再按 RBAC（阿尔巴克）校验角色。业务层还会检查作品的 userId，避免用户修改别人的作品。

一句话：

> “权限不是只做前端路由拦截，而是 JWT 鉴权、RBAC 路径控制和资源归属校验三层一起做。”

### 3.2 模板到作品

> **是什么：** 用户在首页或模板中心搜索模板，点击使用后进入编辑器。
>
> **为什么：** 模板让没有设计能力的用户也能快速开始创作。
>
> **怎么做：** 模板的标题、分类和标签用于搜索；用户点击使用时，后端复制模板的 Canvas JSON（看挖死 杰森）到用户自己的 user_design，而不是直接修改平台模板。

一句话：

> “模板是平台资产，作品是用户资产。创建作品时复制画布 JSON，保证模板不被用户编辑污染。”

### 3.3 编辑器效果：选中、拖拽、缩放

> **是什么：** 点击文字、图片或形状会出现选中框，拖动可以移动，四个角可以缩放；画布可以放大、缩小、适应窗口。
>
> **为什么：** 这是在线设计平台最核心的直接操作体验。
>
> **怎么做：** 每个图层用 DOM（迪欧艾姆）绝对定位，位置来自 Canvas JSON。Pointer Events（坡因特 伊文茨）记录拖拽起点；屏幕位移除以 scale（斯凯尔）换算成画布坐标。选中框和四角手柄由 CSS（西艾斯艾斯）渲染，画布缩放使用 `transform: scale()`。

一句话：

> “缩放只改变显示比例，不改原始坐标；拖拽时再除以 scale，还原成真实画布坐标，所以放大后拖动不会漂移。”

### 3.4 自动保存和版本冲突

> **是什么：** 改完内容后系统自动保存，顶部会显示保存中、已保存、保存失败或版本冲突。
>
> **为什么：** 设计操作频繁，手动保存容易漏；多人同时保存不能后提交覆盖先提交。
>
> **怎么做：** 前端 900ms 防抖保存，30 秒定时兜底，离开页面用 keepalive（凯普阿赖夫）补一次保存。请求带 revision（瑞威申），后端按“作品 ID + 用户 ID + revision”条件更新；更新失败返回 409，前端保留本地草稿并提示重新加载。

一句话：

> “revision 就是乐观锁版本号。它解决的是静默覆盖问题，不是单纯的更新时间展示。”

### 3.5 多人协作效果

> **是什么：** 用户能看到其他成员的彩色光标、图层锁和在线状态。
>
> **为什么：** 多人编辑同一张海报时，要减少重复操作和互相覆盖。
>
> **怎么做：** 同浏览器标签使用 BroadcastChannel（布罗德卡斯特 钱诺），不支持时回退 localStorage（洛口 斯托瑞至）；跨客户端使用 SSE（艾斯艾斯伊）推送事件。光标最多约 40ms 发一次，文档更新约 120ms 合并一次；最终保存仍以 revision 乐观锁为准。

一句话：

> “SSE 负责让用户及时看到变化，revision 负责最终不丢数据；实时通知不能替代数据库并发控制。”

### 3.6 导出 PNG/JPEG

> **是什么：** 用户可以选择 PNG 或 JPEG，选择 1 到 4 倍分辨率和 JPEG 质量后下载图片。
>
> **为什么：** 用户最终需要把编辑结果用于海报、商品图或营销素材。
>
> **怎么做：** 导出前先校验会员额度，再创建离屏 Canvas（看挖死），按图层顺序绘制背景、文字、形状和图片，最后生成 Data URL（戴塔 优艾尔）并通过下载链接保存到本地。

一句话：

> “编辑器的渲染现在是 DOM/CSS，但导出时把同一份 Canvas JSON 重新绘制到离屏 Canvas，得到真实图片文件。”

### 3.7 AI 生成效果

> **是什么：** 用户提交提示词后，弹窗先显示转圈加载，完成后展示图片、视频或失败原因。
>
> **为什么：** AI 调用耗时不稳定，也可能失败，不能一直阻塞浏览器请求。
>
> **怎么做：** 接口先创建 ai_task 并返回 taskId（塔斯克 艾迪）；后端在 Java（加瓦）虚拟线程中调用 Provider（普罗外德），前端每 1.5 秒轮询任务状态。成功显示结果 URL，失败显示 errorMsg（艾若 麦斯基）。

一句话：

> “AI 采用异步任务而不是同步接口，前端拿 taskId 轮询，后端保存状态和失败原因，密钥不会暴露到浏览器。”

### 3.8 AI 抠图效果

> **是什么：** 上传图片后，页面展示原图、透明背景结果、棋盘格、处理中遮罩、进度条、重试和继续编辑按钮。
>
> **为什么：** 电商和运营常需要快速提取人物或商品主体。
>
> **怎么做：** 文件先通过 URL.createObjectURL（优艾尔 克瑞艾特 欧布杰克特 优艾尔）显示本地预览；浏览器按需加载 Selfie Segmentation（塞尔菲 赛格门泰申）进行人物分割，并在 Canvas 中用 `destination-in` 合成透明 PNG。任务结果继续通过 Provider（普罗外德）和轮询返回。棋盘格、进度条和遮罩是 CSS 效果，不是服务端图片。

一句话：

> “抠图卡片先给本地预览，再轮询异步任务；透明区域的棋盘格和加载条都是 CSS 做的视觉反馈，不代表模型真实进度百分比。”

### 3.9 瀑布流和虚拟滚动

> **是什么：** 模板封面高低错落排列，数据很多时滚动仍然流畅。
>
> **为什么：** 海报封面比例不同，且大量卡片一次性渲染会影响性能。
>
> **怎么做：** 瀑布流用 CSS Multi-column（马尔提 可拉姆）和 `break-inside-avoid`；图片用 lazy loading（雷兹 洛丁）。虚拟列表只渲染可视区加 overscan（欧沃斯坎）范围的元素，用 spacer（斯佩瑟）保留完整滚动高度，ResizeObserver（瑞赛兹 欧布泽佛）测量不定高卡片。

一句话：

> “瀑布流解决不同图片比例的布局，虚拟列表解决大数据量 DOM 渲染；两者解决的问题不同。”

## 5. 高频问答谐音版

### 为什么用 revision（瑞威申），不用更新时间？

> revision 是明确的版本号。客户端拿到 V5，服务端只有数据库还是 V5 才允许更新并变成 V6。更新时间容易受精度影响，语义也没有 revision 清晰。

### 为什么协作用 SSE（艾斯艾斯伊），不用 WebSocket（韦布 萨克特）？

> 当前以服务端向前端推送为主，客户端通过普通 HTTP 上报事件，SSE 实现更轻，适合 MVP。后续高频双向协作、跨实例广播再评估 WebSocket 加 Redis（瑞迪斯）。

### 为什么 AI 要用异步任务？

> AI 调用慢且可能失败。先返回 taskId，前端轮询，后端保存状态和错误信息，既不会卡住请求，也能做额度、审计和 Provider 切换。

### 为什么不让前端直接调用 AI Provider？

> 会暴露 API Key（艾皮艾 凯），也无法统一做会员额度、内容审核、日志和失败重试。密钥与第三方调用必须留在后端。

### 为什么图层用 Canvas JSON（看挖死 杰森）保存？

> 图层的类型和属性变化快，用 JSON 可以让模板初始化、用户保存、版本快照和协作共用一份协议。可搜索的标题、标签和分类仍单独放在数据库字段中。

### 项目还有什么边界？

> 协作目前是 SSE 加 revision，不是 CRDT（西阿尔迪提）或 OT（欧提）级别自动合并；AI 任务是进程内异步，生产可演进为消息队列和 Worker（沃克）；会员支付当前是模拟闭环，真实支付回调仍需接入。
